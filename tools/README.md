# Інструменти перенесення SQLite → Supabase

Два скрипти без зовнішніх залежностей (потрібен лише Python 3.8+ зі стандартним
модулем `sqlite3`).

## Статус

Скрипти написані й **перевірені на реальному PostgreSQL 16.13**: згенерований SQL
застосовано end-to-end, дані звірено. Саме перенесення ще не виконувалось —
вихідної бази SQLite у робочому середовищі немає.

Цільовий проєкт Supabase: **Rushh** (`ljpaplkihpijuxgjfhex`, eu-west-1),
схема `public` порожня.

---

## 1. `sqlite_to_supabase.py`

Читає базу SQLite і генерує SQL для PostgreSQL.

```bash
# подивитись схему, нічого не змінюючи
python3 tools/sqlite_to_supabase.py база.sqlite --inspect

# згенерувати SQL
python3 tools/sqlite_to_supabase.py база.sqlite --out out/
```

Створює в теці `--out`:

| Файл | Призначення |
|---|---|
| `001_schema.sql` | таблиці, первинні ключі, зовнішні ключі, індекси |
| `002_NN_data_<table>.sql` | дані пакетами `INSERT` (розмір пакета — `--batch-size`, типово 500) |
| `003_finalize.sql` | вирівнювання `sequence` для сурогатних ключів |
| `manifest.json` | кількість рядків по таблицях — для звірки |

### Що враховано

- **Порядок таблиць** — топологічне сортування за зовнішніми ключами, батьківські
  раніше за дочірні. Циклічні зв'язки не зациклюють генератор.
- **Типи** — мапінг за оголошеною афінністю SQLite: `INTEGER`→`bigint`,
  `BOOLEAN`→`boolean` (з конвертацією `0/1`), `BLOB`→`bytea` (hex-літерал),
  `JSON`→`jsonb`, `DATETIME`→`timestamptz`, `DECIMAL`→`numeric`.
  Колонка без оголошеного типу стає `text`.
- **Екранування** — усі ідентифікатори в подвійних лапках, тому назви з пробілами,
  ключовими словами й кирилицею працюють. Значення екрануються як рядкові літерали.
- **Ідемпотентність** — `CREATE TABLE IF NOT EXISTS` і `ON CONFLICT DO NOTHING`,
  тому повторний запуск не дублює дані й не падає.
- **Порожні таблиці** — файл даних для них не створюється, сама таблиця створюється.

### Чого скрипт свідомо не робить

- **Не вмикає RLS і не створює політик.** У Supabase таблиці в `public` без RLS
  доступні через API. Політики треба додати окремо — під вашу модель доступу.
- **Не чіпає `auth.users`.** Якщо в базі є користувачі, їх зв'язок із Supabase Auth
  потребує окремого мапінгу ID.
- **Не конвертує тригери, в'юхи й перевірочні обмеження SQLite** — їх у SQLite
  зазвичай мало, але якщо є, їх треба перенести вручну.
- **Не розбирає рядкові дати у нестандартних форматах.** Postgres розуміє ISO-8601;
  якщо у вас дати виду `12/31/2025`, потрібна попередня нормалізація.

## 2. `verify_migration.py`

Звіряє кількість рядків між джерелом і ціллю.

```bash
python3 tools/verify_migration.py база.sqlite --expected out/manifest.json
python3 tools/verify_migration.py база.sqlite --actual '{"clients": 3, "orders": 128}'
```

Повертає код виходу `1`, якщо є розбіжності.

## Порядок перенесення

1. `--inspect` — переглянути схему й погодити мапінг типів.
2. `--out out/` — згенерувати SQL.
3. Прочитати `001_schema.sql` очима: перевірити типи, FK і те, які колонки мають бути
   `NOT NULL`.
4. Застосувати `001_schema.sql` до Supabase (міграцією).
5. Застосувати файли `002_*.sql` **по черзі, в порядку нумерації** — порядок
   задано зовнішніми ключами.
6. Застосувати `003_finalize.sql`.
7. `verify_migration.py` — звірити лічильники.
8. **Налаштувати RLS і політики доступу** перед тим, як відкривати API.

### Обмеження на розмір

Supabase застосовує SQL через HTTP, тому дуже великі файли краще різати:
`--batch-size 200` дає менші запити. Для таблиць від сотень тисяч рядків надійніше
не INSERT-и, а `COPY` через прямий підключ до Postgres (рядок підключення —
у Supabase → Project Settings → Database).
